**Reviewer** Codex · **Date** 2026-11-25 · **Reviewed commit** `d2388cd14f43c97a9b3a4f00a4aceb1a68427b1e` (`git rev-parse HEAD`)

**Scope** `docs/architecture-alpha`, PR #2 and issue #1 as identified in the repository. Reviewed the architecture overview, ADRs, implementation plan, desktop validation, D1–D12, both Claude reviews, and the root README, LICENSE, NOTICE, CONTRIBUTING, THIRD_PARTY_NOTICES and TRADEMARKS. Findings distinguish design inferences from upstream facts. Phase 0 results on the reference workstation remain **[unverified]**.

## 2. Verdict

**Hold architecture approval. Proceed with the disposable Phase 0 spike.** The exact engine artifact must satisfy D1, and the ledger must define which outcomes survive faults and who closes interrupted sessions. Financial results also need a pinned execution-time contract. Approve the desktop ADRs only after an installed package demonstrates authenticated attachment and streaming, worker and service lifecycle, and the chosen XWayland configuration on the reference hardware. These changes preserve the D1–D12 decisions and the headless MCP-first research milestone.

## 3. Ranked findings

### P0 — The engine artifact must satisfy the build-level paper-only boundary

**Evidence.** D1 excludes execution adapters able to reach real accounts. The Phase 1 gate requires their absence throughout the dependency tree. The default NautilusTrader rc9 wheel prescribed by ADR-002 and the desktop spike exposes importable Binance and Interactive Brokers execution factories. The artifact and source checks are in §4.

**Impact.** A Clipper route allowlist and absence of seeded credentials control the supported Clipper flows. They cannot establish that the shipped artifact lacks real-account execution code. The unsandboxed Python strategy worker makes the distinction consequential even in Alpha-R.

**Alternatives.** Qualify a supported simulation-only upstream artifact, build a minimal wheel from the exact upstream tag with an auditable feature list and no Clipper fork, or defer release until a conforming artifact is available.

**Recommended change.** Satisfy D1 as written. Make inspection of the shipped wheel and native module, the list of available execution factories, and clean-install backtest and sandbox smoke tests part of Phase 0. An adapter guarded only by configuration fails the documented artifact gate. Keep provenance and source availability for any rebuilt wheel.

### P0 — Command acceptance, execution and publication have separate failure boundaries

**Evidence.** The [approval sequence](overview.md#7-execution-semantics) consumes an approval in `app.db`, sends a command, inserts a unique ID in the session journal, acts in the sandbox, acknowledges, and then receives events. A service can die after consuming approval and before delivering. A worker can die after receiving a command and before acting, or after a fill and before persisting it. ADR-008 has no rule for the surviving journal, while the plan promises a complete journal. Separately, [SQLite synchronous modes](https://www.sqlite.org/pragma.html#pragma_synchronous) [verified] say WAL `NORMAL` preserves consistency under the documented assumptions but can lose committed transactions after system crash or power loss, with no guarantee confined to one transaction.

**Impact.** A unique key prevents duplicate rows. It cannot by itself persist delivery across service failure, decide whether a prior insert reached the engine, or make an engine mutation transactional with SQLite. An acknowledged or user-visible fill can disappear on power loss if publication gets ahead of durable storage. Readable storage alone cannot substantiate D1’s trade-log promise.

**Alternatives.** Store authorization and durable dispatch together in `app.db`, with a separate single-writer worker journal, or co-locate approval and dispatch state in a single transactional authority at the cost of moving ownership. Either design still has an in-memory engine boundary.

**Recommended change.** Consume the approval and enqueue dispatch together in `app.db` with an immutable command ID, session and worker epoch, intent digest, policy revision and dispatch expiry. The worker stores durable receipts and serializes first delivery and retry handling. The same ID and digest return the existing receipt, and an ID reused with a changed payload returns a conflict. Define receipt, terminal execution outcome, and publication as distinct events. Commit acknowledged approvals and ledger mutations durably, use WAL `FULL`, and publish fills only after the journal and projection commit. When the worker dies mid-command, report interruption with the last durable event and any unresolved receipt. Freeze and end the session on a journal write failure. Reattach only to a proven surviving worker. Exercise crashes around every boundary, lost and concurrent retries, gateway restart with the worker alive, disk-full and abrupt system loss.

### P0 — Define a single terminal owner and lifecycle contract for paper

**Evidence.** The overview assigns the ledger to the worker alone (§§2, 7), workers deliberately survive service restart (§2), and the service reports stopped or interrupted sessions. D1 requires a durable end reason and the spike tests restarting the service with a live transient worker. A dead worker cannot write its own terminal event. The policy for an active worker at logout is unspecified. **[verified]** Lingering keeps the systemd user manager eligible to continue after logout. [systemd `loginctl`](https://www.freedesktop.org/software/systemd/man/latest/loginctl.html)

**Impact.** Service shutdown can leave an active worker behind or mislabel a still-running session. A crash can leave a permanently running projection. A new process could also take ownership of an old session during a race unless ownership fencing has a terminal rule.

**Alternatives.** Keep the worker as sole live writer and let the service append one terminal record after acquiring the dead worker’s fenced lease, or make a durable service-owned terminal record authoritative and include it in every export.

**Recommended change.** Use the same sealed ledger for clean and interrupted endings. Specify exclusive terminal takeover after validating worker identity and acquiring a stable per-session lease, then record interruption exactly once and make the session permanently non-runnable. Persist launch intent and worker generation before starting a unit so the service can discover and adopt it after a restart. Define explicit stop admission/drain behavior and what happens to workers on logout, package replacement and reboot. Use SQLite’s snapshot backup mechanism for online journal export. Record ordered event IDs, feed identity and sequence, policy and model revisions, and effective and observed timestamps. Mark data unavailable for future replay if the provider terms bar retention. Fault tests need outstanding orders and an active worker at shutdown. [SQLite Online Backup](https://www.sqlite.org/backup.html)

### P0 — Establish financial truth at the pinned execution boundary

**Evidence.** Overview §§6–7 and ADR-013 promise reproducibility and shared execution models while leaving event attribution, split treatment and fill policy partially defined. The pinned backtest can fill against a close the strategy just saw (§4). The proposed `(open, close]` rule assigns a marker to one bar. It cannot identify the feed event that actually triggered a queued order’s fill. Four decimal places specify storage precision and leave order tick validation open.

**Impact.** Same-bar fills, early opens, missed half-day boundaries, fictitious split P&L and arbitrary intrabar order can all be deterministic. Identical results on repeated runs prove repeatability. An independent ledger is needed to establish economically plausible outcomes.

**Alternatives.** Require a subsequent observable matching event after the signal, or expose same-close settlement as a separately labelled simulation convention with explicit limits. Restrict either choice to calendar, session and feed combinations covered by fixtures.

**Recommended change.** Default to the first eligible matching event after the decision’s data watermark. Require the Phase 0 fixture to show how the pinned engine implements it. Read exact manifest files, pin the exchange calendar and instrument metadata, and keep UTC event identity, availability, submission and execution times separate from chart labels. Specify warm-up cutoffs, half-days and DST, tick and lot validation, and fail closed over known splits. Run an independently calculated expected ledger through the packaged backtest and replay sandbox. Cover callback timing, partial fills, cost basis, realized and unrealized P&L, insufficient cash, and competing stop and target orders with ambiguous OHLC paths. Instantiate shared versioned fill, fee and latency specifications separately and document expected mode differences. Define order-level fee minimums and caps across fills, rounding, fees by effective date, price-only returns, settlement omissions and metric formulas. Recheck policy before dispatch, reserve exposure across pending and working orders, enforce price collars through execution constraints, and test stale feeds and halt/cancel ordering. The full fixture suite gates the affected phase.

### P0 — Demonstrate the installed desktop boundary before approving ADR-016/017

**Evidence.** The [desktop spike](desktop-validation.md#go--no-go) is unexecuted. Its Go list omits an authenticated read/event path and accepts GPU performance in either display mode, although D7 chooses XWayland by default. Overview §§2, 4 and 8 use a dynamic loopback port, a narrow CSP, a bearer header, authenticated discovery and webview WebSockets. [WHATWG WebSocket API](https://websockets.spec.whatwg.org/#the-websocket-interface) [verified] exposes URL and subprotocols as constructor inputs and provides no custom authorization header. Sending a reusable bearer to a discovered port before the service proves its identity also makes the spoofed listener test incomplete.

**Impact.** The package can launch successfully while its read stream, reconnect, scopes or CSP fail. A callback or development harness that receives valid events says little about authentication on an installed Tauri webview.

**Alternatives.** Keep direct authenticated REST with authenticated fetch streaming or revision polling, use an expiring single-use WebSocket ticket tied to instance, origin and scope, or use a thin Rust transport bridge with generated client types retained. For discovery, use an OS-authenticated bootstrap or a server challenge proof which never transmits a reusable credential to an unverified endpoint.

**Recommended change.** Add installed-package Go criteria for authenticated reads, writes and subscriptions, actual Host/Origin values on HTTP and streams, exact dynamic CSP, credential expiry/rotation, spoof rejection and concurrent clients. Handle native requests without Origin explicitly. If WebKitGTK emits an opaque origin, prove a different transport before authorizing browser traffic. Declare custom commands through `AppManifest::commands`, give each window only its required grants and deny navigation and new windows through explicit hooks. Keep reusable bearers out of URLs and traces. Bind worker IPC to its owner and generation in a private runtime directory. Require the default XWayland configuration, including detached-window restore, to pass. If only Wayland passes, record the failure and bring the evidence back for a decision under D7 and D10.

### P1 — Make the packaged Python prefix work after staging

**Evidence.** The packaging instructions assume `uv venv --relocatable` will move alongside bundled CPython. The isolated reproduction in §4 lost its executable after the staging path moved. Debian runtime libraries remain system dependencies.

**Impact.** The shell can launch while the user unit, CLI and MCP fail to start Python. A test run on a build machine can pass while implicitly using the builder’s still-present interpreter.

**Alternatives.** Construct the venv against a fixed installed prefix, or repair final interpreter links and `pyvenv.cfg` deterministically when assembling the package.

**Recommended change.** Choose a fixed package prefix and test it on a clean install after removing build paths and caches. Install from locked non-editable wheels and use package launchers that invoke the installed interpreter directly. Verify native imports and ELF dependencies, service, CLI and MCP with no developer environment, and separate offline launch from package dependency acquisition. Exercise active-work upgrade and uninstall, including user-manager reload and preventing mixed-version workers. This proof belongs in Phase 0 before ADR-017 approval.

### P1 — Specify MCP grants and authority before Phase 1

**Evidence.** ADR-006 and the overview’s scope matrix name `research:read`, workspace read/write and `paper:prepare`. The Phase 2 headless journey needs import, validation, job submission and cancellation. Overview §8 also lists paper reads and an unnamed safety scope. The actor appears alongside caller-supplied REST mutation metadata (§8). D2 and ADR-007 require human approval for AI order-changing actions, while an MCP `emergency_stop` can cancel orders (§§7–8).

**Impact.** Implementations will either overgrant a convenient shared token or strand the canonical MCP journey. Tool discovery and MCP metadata do not establish an application principal. Risk containment and stopping are themselves financial capabilities.

**Alternatives.** Explicitly allow gated de-escalation through MCP, or leave order-affecting stops on the approved human surfaces. For research, start with one write/compute grant or make dataset publication and execution individually assignable.

**Recommended change.** Publish the capability matrix now. Include research import/execute, workspace read/write, paper read/prepare and any separately approved stop capability. Use per-client server-minted grants with rotation and revocation, an allowlisted absolute stdio launcher, and server-derived actors. Refuse approval and policy changes in the shared application enforcement, including when a tool routes through a different API entry point. Keep flatten and re-enable outside any safety grant. Make the stdio adapter disposable and keep job and session lifetime in the service and workers. Test invocation as well as tool discovery, direct scoped calls, subscription denial, reconnect/retry, cancellation ownership and durable jobs after host exit. Keep application logs on stderr and scrub SDK telemetry with the same policy as tool outputs. [MCP stdio specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio) · [SDK 2.0 release](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.0.0)

### P1 — Bind strategy approval to the executable snapshot before Phase 2

**Evidence.** ADR-010 and D9 trust an acknowledged editable file hash. The plan registers strategies by hash and immediately runs headless backtests. Overview §§7–9 provide `validate_strategy` and `run_backtest` but omit the actual acknowledgement and import policy.

**Impact.** A validated entry file can load a changed helper, dynamic dependency, configuration or symlink. Importing for validation can execute Python before approval. This weakens both the D2 mistake barrier and the reproducibility manifest, including for an MCP client without shell privileges.

**Alternatives.** Begin with approved self-contained strategy files and a pinned trusted dependency set, or define content-addressed bundles with an explicit import and configuration manifest.

**Recommended change.** Start with the first option. Snapshot the exact bytes and allowed inputs during registration, bind approval and runs to that immutable version, validate without executing, and add the human CLI acknowledgement to the headless journey. Test changed content between prepare and launch, out-of-root paths, symlinks and modified imports. Confine file ingestion to user-staged roots or pre-registered IDs and enforce size, schema and job limits. Record that the acknowledged strategy runs with current process permissions. For the live-feed phase, decide whether the data client and provider key stay in that same process or move behind the feed boundary before introducing credentials.

### P1 — Audit verification cannot establish human presence or journal completeness

**Evidence.** D2, ADR-007/015 and overview §9 claim external audit edits are detectable. The chain and its head share the same writable trust domain. D2 also says WebAuthn needs no API change, and Claude review 2 says future WebAuthn holds under both display modes.

**Impact.** A valid prefix or fully recomputed unanchored chain can pass verification. A WebAuthn assertion establishes the expected key, challenge, origin and required authenticator flags. Whether the displayed trade matches the signed digest, or whether a process controlling the verifier can reinstate weaker authorization, requires separate guarantees. [W3C WebAuthn assertion verification](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion) [verified].

**Alternatives.** Keep the chain as a local integrity check, or add an independently trusted checkpoint for a stronger claim. Future authorization can use a protected verifier and trusted presentation or a separate approval channel.

**Recommended change.** Keep D2 and state the chain’s limits. Test row changes, truncation and a consistent rewrite separately, and disclose what passes. Specify a versioned approval envelope now with canonical intent, session/actor/policy binding, expiry and explicit evidence type. Leave the exact future API open. Before an untrusted or real-money tier, protect enrollment, verifier, policy and confirmation display and evaluate the full approval flow on supported platforms.

### P1 — Define stream and platform contracts before foundation work

**Evidence.** Overview §§5, 8 and 11 define per-entity revisions, a per-stream monotonic sequence, snapshots after gaps, transient Linux workers and prospective Windows Job Objects/named pipes. The documents leave stream identity/filtering, service generation, snapshot/cursor atomicity, worker adoption and graceful shutdown unspecified. **[verified]** With Windows `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, closing the last job handle kills the associated processes. [Microsoft Job Object limits](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information)

**Impact.** A subscriber can miss a change between snapshot and stream registration, see artificial gaps after filtering, or treat an old cursor as current after restart. A launcher trait alone cannot express Windows adoption and restart semantics, profile locks, endpoint ACLs and shutdown ordering.

**Alternatives.** Use revision polling initially, or retain push with stable subscriptions and replay. Make the service an OS-managed per-user process wherever feasible, or give the future Windows launcher an explicit ownership and recovery contract.

**Recommended change.** Define snapshot and cursor from one read, instance epoch, bounded replay or resnapshot, and entity revisions for conflict checks. Define how versions and credentials change across upgrade and reattach. Specify launcher and worker interfaces in terms of ownership, fencing, timeout, cancellation and adoption. Keep systemd, Unix sockets and `flock` in Linux adapters. Design the future Windows worker supervisor to hold the job handle across gateway restarts and define the named-pipe ACL and per-profile lock contract. Leave Windows implementation to its own phase.

### P1 — Make the package and licensing obligations release evidence

**Evidence.** Overview §§4 and 12 state a replaceable Nautilus wheel meets LGPL, phase 4 gathers three language inventories, and the root notices are placeholders. The current contribution policy implements D3’s CLA merge hold and records packaged source obligations. **[verified]** LGPLv3 §4 sets conditions for conveying combined works. AGPLv3 §§6 and 13 set source obligations for the applicable distribution and modified-network-use cases. [Contribution rules](../../CONTRIBUTING.md) · [LGPLv3 §4](https://www.gnu.org/licenses/lgpl-3.0.en.html#section4) · [AGPLv3 §§6, 13](../../LICENSE)

**Impact.** Package-owned files and replacement instructions may make an ordinary wheel effectively irreplaceable for a recipient. A lockfile inventory alone misses the bundled interpreter, its native libraries and the chart artifacts. An approved CLA preserves only the rights actually granted. A service boundary alone leaves combined-work and deployment-specific licensing questions open.

**Alternatives.** Validate a supported compatible wheel override/replacement path and corresponding source mechanism, or provide documented source and rebuild/relink materials appropriate to the conveyed artifact. For Cloud, review the actual deployment and licences once the boundary is concrete.

**Recommended change.** Before Phase 4 distribution, record the exact runtime, wheel, JS, Rust and native payload, checksum/source/rebuild mapping, per-component notices, applicable licence texts and a working way for recipients to run the package with a compatible replacement. Demonstrate it after clean install and document persistence across upgrades. Include AGPL corresponding source for the shipped build and have counsel check the chosen LGPL path and D3’s CLA before external merges. Keep trademark requirements distinct from copyright notices and upstream attribution.

### P2 — Small research slices need measurable gates

**Evidence.** The plan already removed the old aggregate estimate and puts MCP before UI. Phase 0 nonetheless couples full install/upgrade, packaged engine, lifecycle, GPU, multi-monitor, dual-window convergence and E2E, before interfaces have been proved. Overview §10 has provisional targets without repeat counts, a defined load mix, a launch timeout rule, or a committed memory budget. Overview §1 still leaves Leviathan undefined.

**Impact.** Cosmetic demos can consume the timebox while substantive gate failures remain open. Chart rendering metrics and interactivity evidence are easiest to misread across hosts, display modes and runtime versions.

**Alternatives.** Split Phase 0 into minimal independently reportable proofs, or expand the timebox based on actual failure categories. Keep one docked window for the first desktop slice, then test the already required detached flow.

**Recommended change.** Put packaged engine, auth and worker lifecycle ahead of styling. Use a fixture and scripted repeat counts for performance, report warm and cold samples with version/GPU details, and mark any unexecuted gates explicitly. Preserve the D4 dependency order and D11’s one-package scope. Define Leviathan in a sentence or remove the undefined integration note.
